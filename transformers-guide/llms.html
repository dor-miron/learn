LLMs & Decoders.

A short history of why your favourite chat model is technically a “decoder” with no encoder — even though it very obviously reads your prompt. The terminology is a historical accident, but the architectural choice it points to is the whole reason these models scale.

The 2017 Transformer — where the names come from

The original Transformer paper (“Attention is All You Need”, Vaswani et al.) was about machine translation. You feed in an English sentence, you want a French sentence out. The architecture had two stacks:

Why “decoder”?

What distinguishes the decoder block from the encoder block in the original paper isn’t the input or the output — both stacks see tokens, both produce vectors. The differences are structural:

  1. The decoder’s self-attention is causal. Token i can only attend to tokens 1…i. The encoder’s is bidirectional.
  2. The decoder has an extra sub-block, cross-attention, where it queries the encoder’s output. The encoder has no such thing.
  3. The decoder is asked to generate output autoregressively — predict the next token given everything generated so far. The encoder isn’t producing a sequence; it’s producing one vector per input position for later use.

So “decoder” in this terminology means: causal self-attention, autoregressive generation, optionally cross-attends to something else. “Encoder” means: bidirectional self-attention, produces representations for downstream use.

Now — the punchline. GPT and friends keep the decoder, drop the encoder, and drop the cross-attention. What’s left is a stack of blocks doing causal self-attention + feed-forward. That stack is, structurally, “the decoder of a Transformer minus its cross-attention to the encoder.” The name decoder-only just describes which half of the 2017 architecture they kept.

“But isn’t the prompt encoded first?”

This is exactly the question you asked, and it’s a sharp one. When you give GPT a 200-token prompt, the model definitely does something with it before generating a reply — it has to compute representations for all those tokens. Doesn’t that count as encoding?

Yes, in the colloquial sense. No, in the architectural sense. Here’s the distinction:

Encoder (in the 2017 sense)

  • A separate stack of layers.
  • Uses bidirectional self-attention — each input token sees every other.
  • Produces a set of vectors that the decoder accesses via cross-attention.

What a decoder-only LLM does with a prompt

  • The same stack that will generate the reply.
  • Uses causal self-attention — prompt token i only sees prompt tokens 1…i.
  • Produces hidden states for each prompt token, and they’re reused via the KV cache during generation.

So yes, the prompt is being processed — in industry slang this is called prefill. But it’s done by causal self-attention in the same stack that will then start generating, not by a separate bidirectional encoder. There is no architectural notion of “encode the prompt, then start decoding.” It’s all one operation.

The clean way to say it

A decoder-only LLM has one machine. That machine does causal self-attention. We call the first big pass through it “prefill” (it just happens to be parallelisable because we already know all the prompt tokens) and the subsequent token-by-token forward passes “decode”. There’s no separate “encode the prompt” module — there’s just causal attention being applied to a growing sequence.

The three families, side by side

Why decoder-only won the LLM race

This wasn’t obvious in advance. Around 2020 it was an open question. The community ended up converging on decoder-only for a few converging reasons:

1. Every token contributes to the loss.

In a causal language model, the training objective is “given tokens 1..i, predict token i+1.” That means every single position in every single training document gives a gradient signal. A document with 2 000 tokens generates 2 000 supervised predictions. By contrast, BERT-style masked language modelling masks ~15% of tokens, so 85% of positions in each document don’t directly contribute. Decoder-only training is just more sample-efficient per token of corpus.

2. The same model can do almost any task.

Anything you can frame as “here is some text, what comes next” the model can attempt. Translation: “English: X   French:” and let it complete. Classification: “Review: X   Sentiment:” and let it complete. Code: write the function signature and let it complete. In-context learning — the ability to learn from examples in the prompt without weight updates — is a property that fell out of large decoder-only models almost by accident, and it’s the foundation of every modern chat interface.

3. Architectural simplicity.

One stack. One attention pattern. No coordination between encoder and decoder during training. Easier to scale, easier to parallelise across GPUs, easier to engineer. When you’re training models with thousands of accelerators, “simpler” turns into “more efficient” turns into “cheaper per quality unit.”

4. Generation falls out for free.

BERT can’t fluently generate text — it wasn’t trained for it. T5 can, but you pay for the encoder’s parameters even at inference time, when many tasks don’t need a separate “read” pass. Decoder-only models can do both reading and writing in one machine, with one cost model.

The deep reason, in one sentence

Causal language modelling is a maximally dense, maximally general training signal — every token in every document predicts the next one — and any text-based task can be framed as “continue this sequence.” That combination scales further than the alternatives, full stop.

What that means for how an LLM actually runs

Two things follow from the decoder-only design that are worth understanding even at a conceptual level:

The KV cache

At generation step t, the model needs the keys and values of every prior token to compute attention. Computing them again from scratch every step would be quadratic; instead, after every forward pass you cache the K and V vectors. Generating token t+1 then becomes: compute Q for the new token, attend to the cached Ks and Vs, predict, append the new K/V to the cache, repeat. This is why long-context LLMs have memory pressure proportional to context length × layers × model width — the KV cache is the dominant cost at inference.

Pretraining vs post-training

A “raw” pretrained LLM is a next-token predictor. It will happily complete “The capital of France is” with “Paris,” but it will also complete “Write a haiku about Paris.” with another instruction-shaped sentence, not with the haiku. To turn a base model into a chat assistant, three further stages are layered on:

  1. SFT (supervised fine-tuning) on examples of (instruction, good response) pairs.
  2. Reward model training — train a separate model to score responses by human preference.
  3. RLHF/DPO — optimise the LLM so that its outputs score well under the reward model (RLHF) or directly match preferred-over-rejected pairs (DPO).

The architecture stays the same throughout. Post-training just changes what kind of continuations the same machine produces.

Recap

  • “Decoder” in transformer terminology means: causal self-attention, autoregressive generation.
  • The 2017 Transformer had an encoder and a decoder for translation. Modern LLMs keep only the decoder — minus its cross-attention — hence “decoder-only.”
  • The prompt is processed in the same stack as the generated text, in a step called prefill. There’s no separate encoder.
  • Decoder-only won because every token gives a training signal, any task can be framed as continuation, the architecture is simple, and generation is built in.
  • The KV cache makes per-token decode cheap; everything else (RLHF, tool use, multimodality) is a layer on top of the same core.
