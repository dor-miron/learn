A short interactive field guide

The background is a bag of pixels you’ve already seen

ViBe throws away the statistics. Each pixel remembers twenty raw values it has been in the past, and a new value is background if it lands close to a couple of them. No Gaussians, no histograms, no learning rate — and it runs faster than everything it replaced.

The question is “which pixels are new?”

Point a camera at a parking lot and leave it there. Almost every pixel is boring: the same asphalt, the same wall, the same patch of sky, frame after frame. What you care about is the small fraction that isn’t boring — the car pulling in, the person walking past. Background subtraction is the operation that separates the two: in, a video from a fixed camera; out, a binary mask marking every pixel that doesn’t belong to the scene’s idea of “normal”.

It is the cheapest useful primitive in video analysis. It runs before the expensive things — you segment first, then only run a classifier on the blobs, or feed the blobs straight into a multi-object tracker. On a fixed camera it costs a few operations per pixel and gives you most of what a detector would, without a detector.

The naive attempts fail in instructive ways, and the failures are what ViBe is designed around.

Difference consecutive frames

Threshold |It − It−1|. Dead simple, and almost useless: a uniformly-colored car produces a detection only at its leading and trailing edges, because its middle looks the same as its middle did last frame. Stop the car and it vanishes entirely.

Keep a running average

Maintain one background value per pixel, B ← (1−α)B + αI, and threshold the residual. Now stationary objects survive. But a single average per pixel assumes the background is unimodal, and plenty of backgrounds aren’t.

That last failure is the important one. Consider a pixel that sits on the edge of a leaf swaying in the wind. Half the time it’s dark green leaf; half the time it’s bright sky. Its average is a murky teal — a color that pixel is never actually observed to be. A model built on that average flags the pixel as foreground essentially always. The same goes for rippling water, a flickering monitor, a flag, an escalator.

The canonical fix, and the field’s workhorse for a decade, was to make the per-pixel model multimodal: model each pixel as a mixture of K Gaussians (Stauffer & Grimson, CVPR 1999), later with K chosen adaptively per pixel (Zivkovic, ICPR 2004 — this is OpenCV’s MOG2). Now the leaf pixel gets a green component and a sky component and both count as background. It works. But look at what you’re doing: you are fitting a parametric probability density, online, per pixel, from a handful of effective observations, with a learning rate you have to tune, and you need a training period before the fit means anything.

The key insight

ViBe’s answer is to not estimate a density at all. If what you want to know is “have I seen this value here before?”, then don’t fit a distribution and evaluate it — just keep some of the values and look. The paper is blunt about it: “no estimation of the pdf of the background pixel is performed”; instead we “build a model with real observed pixel values.”

The model is twenty numbers per pixel

Every pixel location x owns a set of N samples, each one an actual value that pixel took in some previous frame:

M(x) = { v1, v2, …, vN }

That’s the whole model. No means, no variances, no weights, no component count, no timestamps. For a 640×480 greyscale video with N = 20 it is a byte[480][640][20] — twenty bytes per pixel, and the paper’s pseudo-code declares exactly that.

Classification is counting, not fitting

Now a new frame arrives and the pixel has value v(x). Draw a sphere of radius R around it in color space, SR(v(x)), and count how many of the N stored samples fall inside. If at least #min of them do, the pixel is background:

#{ SR(v(x)) ∩ { v1, v2, …, vN } } ≥ #min

With the paper’s defaults — N = 20, R = 20, #min = 2 — the entire decision procedure reads: “of the twenty values I remember being, are at least two of them within 20 grey levels of what I see right now?” If yes, background. If no, foreground. That is the complete classifier.

Two properties of this rule are worth dwelling on, because they are where the method gets its robustness.

The model is multimodal by construction. Look again at the figure: the leaf-and-sky pixel simply stores some green samples and some blue ones, roughly in proportion to how often it is each. Nothing had to decide that this pixel needs two components while its neighbor needs one. There is no K. The multimodality that MOG2 achieves by fitting and pruning Gaussians, ViBe gets by the trivial expedient of remembering.

#min = 2 is a deliberately tiny threshold, and it is doing real work. Requiring two matches rather than one says “I’ve seen a value like this here before, and not just once, by accident” — it filters out a single stale or noisy sample that happens to sit near the current value. Requiring only two rather than ten means a background mode needs to occupy just 10% of the sample set to be recognized, so rare-but-real background states (the leaf position that only occurs in a gust) still get respected. The paper notes that sensitivity is really governed by the ratio #min/N, and that with a stable background you can even drop to #min = 1.

Gotcha: the defaults you read are not the defaults you get

The 2011 paper specifies a Euclidean sphere with N = 20, R = 20, φ = 16. The authors’ own released C code ships N = 30, R = 10, φ = 8 and computes an L1 distance for color (|Δr| + |Δg| + |Δb| ≤ 4.5R), not a Euclidean one — the README says outright that “parameters used in the implementations have changed”. And the 2009 ICASSP version used R = 30 with no φ at all. Quote 20/20/2/16 as the paper’s values, not as canon.

Why not just keep a buffer of the last N frames?

This is the obvious version of the same idea — a ring buffer of the last twenty observed values — and it is roughly what earlier sample-based work did. It has one crippling property: twenty samples buy you exactly twenty frames of memory, less than a second of video. A background that changes on the scale of minutes (sun moving behind a cloud, a car parked and left) is invisible to it, and the only fix is more memory, linearly.

What you actually want is a set of samples whose ages span a long window — a few recent, a few from a minute ago, maybe one from five minutes ago. Committing to fixed ages is bad too, because you’ve then hard-coded a timescale. ViBe’s resolution is to make the age distribution fall out of a random replacement rule, which buys a theoretically infinite time window from a fixed twenty bytes. That argument is the subject of the next page, and it’s the reason ViBe is not just “SACON with better marketing”.

What it costs

Almost nothing, and for a subtle reason. The comparison loop exits as soon as #min matches are found, so a typical background pixel — the overwhelming majority of the frame — is settled after about two comparisons, not twenty. (The released implementation sharpens this further with a trick the paper never mentions: it swaps matching samples to the front of the buffer, so the next frame usually matches on the first two probes.) Appendix B of the paper works it out at roughly 2.5 byte-comparisons plus 1.5 counter comparisons per pixel — comparable to a first-order recursive filter.

The headline number: 200 frames per second on 640×480 video, on a 2.67 GHz Core i7 in C, about five times faster than the Intel-optimized GMM implementations it was compared against. A downscaled variant exceeds 350 fps.

A number that gets misquoted

You will see “ViBe needs one byte and one comparison per pixel”. That figure belongs to the deliberately downscaled variant described in the same paper, not to ViBe proper. Full ViBe costs N bytes per pixel per channel — 20 B/px greyscale at the paper’s defaults, 60 B/px for RGB, and 90 B/px at the code’s N = 30. That is genuinely more memory than MOG2 uses; ViBe trades memory for arithmetic, which is the right trade on modern hardware but is a trade.

It starts working on frame two

Most background models need a training sequence — tens or hundreds of frames of empty scene — before their statistics mean anything. ViBe fills its model from a single frame. The trick is to borrow across space instead of time: assume neighboring pixels share a similar temporal distribution, and populate each pixel’s model with values drawn at random from its 8-connected neighborhood in frame 0.

M0(x) = { v0(y | y ∈ NG(x)) }

Locations y are drawn uniformly and with replacement, so a given neighbor may be picked several times or not at all — duplicates in the model are expected, not a bug. From frame 2 onward you have a usable segmentation. This also means the recovery procedure for a catastrophic scene change (someone flips the lights on) is simply to throw the model away and re-initialize from the current frame — a one-frame operation.

The cost of this shortcut is that anything moving through frame 0 gets baked into the model as if it were scenery, and leaves behind a ghost when it moves on. Handling that gracefully is one of the things the update policy is built to do.
