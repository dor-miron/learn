A short interactive field guide

Track anything with a click

You draw one box on frame 1 — no detector, no labels, no class. A discriminative correlation filter (KCF, CSRT) learns that patch and re-finds it every frame, at hundreds of frames per second. Here's the trick that makes it work, and why it's faster than it has any right to be.

One box, then follow it

Here is the whole problem. A video is playing. You draw a single rectangle around something on the first frame — a person, a ball, a drone, a coffee mug — and the computer follows that thing for the rest of the clip. No object detector. No class label. No training set of mug photos. Just this region, now, follow it.

This is called single-object or model-free tracking, and the “model-free” part is the whole personality. A detector-based tracker like ByteTrack runs a trained network on every frame to find all the people (or cars, or whatever it was trained on) and then stitches those boxes into trajectories. It knows what a person looks like in general. A correlation-filter tracker knows nothing in general. Everything it will ever know about the target is whatever was inside the box you drew, refined frame by frame.

The key tension

Because it learns the target on the fly, a correlation filter tracks anything you can put a box around — no retraining, no classes. That same fact is the curse: it can be fooled by look-alikes, and it can quietly forget what the target was. Power and brittleness come from the same root.

The click itself is mundane — in OpenCV it’s cv2.selectROI, which lets you drag a box and hands you (x, y, w, h). The interesting question is what happens next: given one labeled patch, how do you re-find it in the next frame, and the next, fast enough to keep up with video? The answer the KCF and CSRT trackers give is a genuinely clever piece of signal processing.

A correlation filter is a template that peaks

Start with the obvious idea: template matching. Keep the patch from frame 1 as a little template. In the next frame, slide it over every location, measure how well it matches, and declare the best-matching spot the new position. “Slide a template and measure match at every offset” is exactly cross-correlation — a sliding dot product.

Done naively this is mediocre. The raw patch correlates highly with anything of similar brightness or texture, so the response is a mushy blob, not a confident spike, and it drifts onto whatever is bright nearby. We want something sharper.

Here is the move that gives the method its name. Instead of using the raw patch as the template, we learn a filter — call it h — with one demand: when h is correlated with the training patch, the output should be a clean 2D Gaussian bump centred on the target and approximately zero everywhere else. We’re not storing an appearance; we’re solving for the filter that produces a peak. That’s a regression problem (least-squares with a ridge penalty), and its solution is the correlation filter.

Two things fall out of this picture for free. The peak’s location tells you where the target moved. The peak’s height tells you how confident the match is — a peak that collapses into a low, ambiguous bump is the tracker’s way of saying “I’ve lost it.” We’ll lean on both later.

Why it runs at hundreds of frames per second

So far this could be slow. To make the filter discriminative — sharp, not mushy — you want to train it against lots of negative examples: the target dead-centre is the one positive, and every off-centre version (where background has crept into the window) should produce a low response. Where do those negatives come from? You shift the patch. Each cyclic shift of the window is a different alignment, and all but the centred one are negatives.

Train ridge regression honestly over all n shifts of an n-pixel patch and you have an n×n linear system — an O(n3) matrix inversion. For a modest 150×150 window that is millions-cubed. Hopeless at video rate. This is where the method earns its keep:

The one idea to remember

The set of all cyclic shifts of a patch forms a circulant matrix, and every circulant matrix is diagonalised by the Discrete Fourier Transform. So in the Fourier domain the giant coupled system falls apart into n independent one-variable equations. Training stops being a matrix inversion and becomes an element-wise divide of two FFTs.

Written out, the linear correlation filter has this closed form (uppercase = the 2D DFT of the lowercase signal, ∗ = complex conjugate, ⊙ = element-wise product, and the division is element-wise):

W = ( X∗ ⊙ Y ) / ( X∗ ⊙ X + λ )

That’s the entire training step: take the FFT of the patch X and of the Gaussian target Y, multiply and divide element-wise, done. Detection is the same shape — one FFT, one element-wise multiply by the filter, one inverse FFT to get the response map. Everything is dominated by the FFT, so the cost drops from O(n3) to O(n log n). That single change is why MOSSE hit 600+ fps in 2010 and KCF runs comfortably past 100 fps on a CPU today.

Where this came from

The trick was introduced for tracking by MOSSE (Bolme, Beveridge, Draper & Lui, CVPR 2010) — “Minimum Output Sum of Squared Error” — a single-channel grayscale filter clocked at 669 fps. CSK (2012) added a kernel; KCF (Henriques, Caseiro, Martins & Batista, TPAMI 2015) added HOG features and the kernel trick. Same Fourier skeleton throughout.

The derivation: circulant structure, diagonalisation, and the kernel trick (KCF)

Ridge regression. Given samples xi with targets yi, ridge regression seeks w minimising Σi(w⊤xi − yi)2 + λ‖w‖2, with the familiar closed form w = (X⊤X + λI)−1X⊤y. Here the rows of X are not independent data — they are all the cyclic shifts of one base patch.

Circulant = diagonal in Fourier. A matrix whose every row is a cyclic shift of the row above is circulant. The key algebraic fact (KCF, §4): a circulant matrix is diagonalised by the DFT matrix F regardless of the generating patch, i.e. X = F diag(x̂) FH. Substitute that into the ridge solution and every matrix in sight becomes diagonal; the coupled system decouples frequency-by-frequency, leaving the element-wise expression W = (X∗ ⊙ Y) / (X∗ ⊙ X + λ). The denominator X∗⊙X is just the power spectrum |X|2.

The kernel trick (this is KCF). KCF runs the same idea in a kernelised ridge regression so it can use a Gaussian or polynomial kernel on multi-channel HOG features. Remarkably, the circulant structure survives kernelisation, and the dual coefficients have the equally cheap form α̂ = Y / (Kxx + λ), where Kxx is the Fourier transform of the kernel auto-correlation of the patch. Still one FFT and an element-wise divide.

The convention that bites people. Because FFT-based correlation puts the zero-shift output at index (0, 0), the Gaussian regression target is centred on the top-left corner and wraps around the edges — not placed in the visual middle. Centre it naively and your peak is off by half a window. The cosine window (below) is applied for a related reason: to suppress the discontinuity where the patch wraps.

The per-frame loop

Putting it together, here is the actual loop a KCF/CSRT tracker runs. It is strikingly short.

Two details in that loop matter more than they look. The cosine (Hann) window multiplies every patch before the FFT, fading its edges to zero so the circular-correlation assumption doesn’t see a hard discontinuity at the boundary. And the online update — the dashed arrow — never retrains from scratch: it linearly blends the new filter into the running one with a small learning rate η (around 0.02 for HOG features), so the model adapts to gradual appearance change while smoothing over single-frame noise.

The loop in pseudocode, and the same thing in OpenCV 
# --- init (frame 1) ---
patch = crop(frame1, bbox) * cosine_window
X = fft2(features(patch))
Y = fft2(gaussian_peak(bbox.shape))   # 2D Gaussian target
W = (conj(X) * Y) / (conj(X) * X + lam)
model_X, model_W = X, W

# --- per frame ---
for frame in video:
    z = fft2(features(crop(frame, last_bbox) * cosine_window))
    response = real(ifft2(model_W * z))      # correlation in Fourier domain
    peak = argmax(response)                  # -> new center (and scale, in CSRT)
    last_bbox = bbox_at(peak)
    # online update: blend, don't replace
    Xn = fft2(features(crop(frame, last_bbox) * cosine_window))
    Wn = (conj(Xn) * Y) / (conj(Xn) * Xn + lam)
    model_X = (1 - eta) * model_X + eta * Xn
    model_W = (1 - eta) * model_W + eta * Wn

In practice you never write this yourself — OpenCV ships it. Note KCF and CSRT live in the main cv2 namespace but require the opencv-contrib-python package (not the base opencv-python):

import cv2
cap = cv2.VideoCapture("clip.mp4")
ok, frame = cap.read()

bbox = cv2.selectROI("pick target", frame)   # drag a box -> (x, y, w, h)
tracker = cv2.TrackerCSRT_create()            # or cv2.TrackerKCF_create()
tracker.init(frame, bbox)

while True:
    ok, frame = cap.read()
    if not ok: break
    found, bbox = tracker.update(frame)       # -> (bool, (x, y, w, h))
    if found:
        x, y, w, h = map(int, bbox)
        cv2.rectangle(frame, (x, y), (x + w, y + h), (0, 255, 0), 2)
    cv2.imshow("track", frame)
    if cv2.waitKey(1) == 27: break

(MOSSE is the exception — it only exists as cv2.legacy.TrackerMOSSE_create().)

The two you’ll actually use: KCF and CSRT

OpenCV ships a handful of these, but two dominate real use, and they sit at opposite ends of the speed–accuracy trade.

KCF — the fast one

Kernelised ridge regression on HOG features (Henriques et al., 2015). Blazing — well over 100 fps on a CPU. Fixed scale: the box never grows or shrinks, and it assumes a rigid rectangle. The right default when the target is roughly constant size and you need speed or many simultaneous trackers.

CSRT — the accurate one

CSR-DCF (Lukežič et al., 2017) adds a spatial reliability map — a per-frame mask confining the filter to the actual object — plus per-channel reliability weights, on HOG + Colornames features. Estimates scale. Roughly 10× slower (~13 fps in the paper) but markedly more robust, especially on non-rectangular targets.

That spatial reliability map is the single most important difference, and it turns out to be exactly the feature that decides whether either tracker survives a busy or changing background — which is the next page’s job. Both questions you came in with — does this work over a changing background? and what about a drone that changes its cross-section? — are really questions about where this elegant little loop breaks.
